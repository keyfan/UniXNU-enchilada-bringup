# Stage 5 GPU — A630 (A6XX GEN1) hw_init register map, derived by the upstream method

**Status: HOST-VERIFIED only.** 2026-11-09, Round 20/50. This document records a
read-only, host-verified deliverable produced by replicating UniXNU's upstream
`pin-before-derive` method for the **first** Adreno generation. It is NOT a GPU
driver, NOT linked into the kernel, reads no MMIO, loads no firmware, starts no
GMU/HFI, submits no command, and renders nothing on the device. No CI build, no
flash, no device verification was performed. Hardware observations would have to
be reported separately from these build results (per `kits/AdrenoFirmware/AGENTS.md`
and `drivers/Adreno740/AGENTS.md`).

## What this document answers

User m26410 「下一轮开始,我想先修复GPU」 and m26417 (learn the Coolapk article and
**reference the upstream GPU-driver adaptation**). Following m12247 「先核验再上机」

*same* pinned-source method upstream uses for A740 — not a rename of sheng's six
GPU archives.

## Why the upstream split matters (architecture, load-bearing)

- **Generation-independent wire ABI** — `oneplus6-ios/work/UniXNU/drivers/Adreno740/NativeAdrenoABI.h`
  (165 lines) and `NativeAdrenoClient.h` (52 lines). Verbatim:
  `struct NativeAdrenoTransport { void *cookie; IOReturn (*call)(void *cookie,uint32_t method,const void *input,size_t input_size,void *output,size_t output_size); };`
  and 「The transport is injected so the same client can drive an IOKit connection
  later and the kernel dispatch core during host qualification.」 The ABI
  (`NativeAdrenoAbiVersion = 2`, `MaxBuffers = 128`, `MetadataBytes = 64`,
  `MaxQueues = 8`, 18 methods) passes only opaque `uint64` handles and
  `struct NativeAdrenoAbiDeviceInfo { uint32_t chip_id; /* ADRENO_CHIPID, e.g.
  0x43050a01 */ uint32_t gmem_bytes; uint64_t gmem_base; uint64_t uche_trap_base;
  uint64_t va_start; uint64_t va_size; uint32_t highest_bank_bit; uint32_t
  ubwc_swizzle; uint32_t macrotile_mode; uint32_t ubwc_version; uint32_t flags;
  uint32_t reserved; };` — the A740 chip id appears only in a comment; GPU facts
  are DATA, not code. `NativeAdrenoBoard.h` (DT `parseIommus`/`parseReg`) is
  likewise generation-independent (「Only the SID is extracted, never a guessed
  context bank.」). `NativeAdrenoFirmware.h` (sha-pin `validate`) is also reusable.
  ⇒ **An A630 GEN1 kernel backend can implement the same wire transport ABI.**
- **Generation-specific registers** — `NativeAdrenoA740HwInit.h` is generated by
  `scripts/derive-a740-hwinit.py` from pinned `a6xx.xml` / `adreno_common.xml` /
  `a6xx_gmu.xml` with **exact A7XX variant selection** and `a6xx_catalog.c`
  (`a740_hwcg`, `a730_protect`). Its comment: 「Generated by scripts/derive-a740-hwinit.py
  from the pinned ... (A7XX variants) ... Dword register offsets. Do not edit by hand.」
  It has `A740_GPU_GMU_AO_GMU_CGC_MODE_CNTL 0x23b09`, 54 hwcg entries, 46 protect
  writes. `NativeAdrenoCpInit.h`, `NativeAdrenoIrq.h`, `NativeAdrenoRing.h` are
  explicitly 「A7XX」 one-shot/IRQ/ring implementations and CANNOT be copied to A630.
- **Consequence** — per the official guide `https://unixnu.com/zh/porting/gpu`
  §1 「其他 GPU 代际需要先实现对应内核后端和编译器支持，再选择前端」 ("other GPU
  generations need a matching-generation kernel backend + compiler support before
  choosing a frontend"). This round delivers the *first* piece of that backend: the
  A6XX-variant register map. The CP/IRQ/GMU cold-start layers remain to be written.

### The decisive generation difference (verbatim from the derived header)

```
#define A630_GPU_GMU_AO_GMU_CGC_MODE_CNTL 0x09309
#define A630_GPU_GMU_AO_GMU_CGC_DELAY_CNTL 0x0930a
#define A630_GPU_GMU_AO_GMU_CGC_HYST_CNTL 0x0930b
```
vs the sheng A740 backend's `0x23b09 / 0x23b0a / 0x23b0b`. This is a real
A6XX-vs-A7XX variant difference from the pinned `a6xx_gmu.xml`
(`<reg32 offset="0x9309" name="GPU_GMU_AO_GMU_CGC_MODE_CNTL"/>`), NOT a guess.
Other A6XX offsets: `A630_RBBM_STATUS 0x00210`, `A630_RBBM_STATUS3 0x00213`,
`A630_RBBM_INT_0_STATUS 0x00201`, `A630_CP_ALWAYS_ON_COUNTER 0x00980`,
`A630_CP_RB_BASE 0x00800`, `A630_CP_RB_CNTL 0x00802`,
`A630_CP_RB_RPTR_ADDR 0x00804`, `A630_CP_RB_RPTR 0x00806`,
`A630_CP_RB_WPTR 0x00807`, `A630_CP_PROTECT 0x00850`,
`A630_UCHE_TRAP_BASE 0x00e09`.

The four A7XX-only names `CP_BV_APRIV_CNTL`, `CP_LPAC_APRIV_CNTL`,
`CP_BV_RB_RPTR_ADDR`, `GRAS_NC_MODE_CNTL` carry `variants="A7XX-"` in the pinned
`a6xx.xml` and are **correctly absent** from the A630 header (50 = 46 + 3 + 1).

Protect table first/last (verbatim):
`{ 0,0x13fc0000},` = `A6XX_PROTECT_RDONLY(0x00000, 0x04ff)` →
`(0x04ff << 18) | 0`; `{31,0x80011c00},` = `A6XX_PROTECT_NORDWR(0x11c00, 0x0000),
/* note: infinite range */` → `(1<<31) | 0x11c00`, written at `count_max-1 = 31`
per `a6xx_set_cp_protect()` (`a6xx_gpu.c:495-501`).

## Honest corrections to the prior feasibility record (load-bearing)

The 2026-11-08 `evidence/stage5-gpu-feasibility.md` and `porting.toml` gpu area
contain claims that this round's broad research partly supersedes. Read-only
subagent research (`fac76115`, web_fetch + jsdelivr + raw.githubusercontent +
gitlab.freedesktop.org + git.kernel.org cgit; web_search unavailable) plus local
pinned-byte re-verification found:

1. **No chip-id MMIO register exists.** `a6xx.xml` has no `CHIP_ID`/`HW_VERSION`
   field; mainline `adreno_device.c find_chipid()` reads the DT `qcom,chipid`
   property (`of_property_read_u32(node, "qcom,chipid", chipid)` with
   `dev_warn(dev, "Using legacy qcom,chipid binding!\n")`), and `adreno_gpu.c`
   sets `adreno_gpu->chip_id = config->chip_id;`. Downstream msm-4.9 KGSL likewise
   reads `qcom,chipid` from DT (`KGSL_DRV_FATAL(..., "No GPU chip ID was
   specified\n")` if absent); `a6xx_reg.h` has no `A6XX_RBBM_CHIPID0`.
   ⇒ `qcom,chipid=<0x6030001>` is matched BY EQUALITY to `a6xx_catalog.c`
   chip_ids `0x06030001/0x06030002`, NOT read from a register. The old
   `next_action` item "source the exact chip-id register offset" is therefore
   impossible as written and is corrected. Safe **read-only** probe registers
   that DO exist (dword offsets): `RBBM_STATUS 0x210`, `RBBM_STATUS3 0x213`
   (`SMMU_STALLED_ON_FAULT`), `RBBM_INT_0_STATUS 0x201`,
   `CP_ALWAYS_ON_COUNTER 0x980`, `CP_RB_RPTR/WPTR 0x806/0x807`.
   `a630_protect_regs[0] = A6XX_PROTECT_RDONLY(0x00000, 0x04ff)` protects the
   first 0x4ff dwords as read-only. PM4 note from `a6xx_gpu.c`: 「For PM4 the GMU
   register offsets are calculated from the base of the GPU registers so we need
   to add 0x1a800 to the register value on A630 to get the right value from PM4.」
2. **The three A630 firmware blobs are PUBLIC, not proprietary-absent.** Verbatim
   `MODULE_FIRMWARE` in `a6xx_catalog.c`: `"qcom/a630_sqe.fw"`,
   `"qcom/a630_gmu.bin"`, `"qcom/a630_zap.mbn"`. git.kernel.org linux-firmware
   cgit (HTTP 200) lists `qcom/a630_gmu.bin` (32768 B), `qcom/a630_sqe.fw`
   (34188 B), `qcom/sdm845/a630_zap.mbn` (14256 B, in the `qcom/sdm845/`
   subdirectory, NOT the `qcom/` root). Note the inconsistency: catalog
   `.zapfw = "a630_zap.mdt"` but `MODULE_FIRMWARE` says `.mbn`; `adreno_gpu.c`
   tries `qcom/<name>` first. The ZAP shader still needs `qcom_mdt_load()` of
   `.mdt` + `.b00`/`.b01` and `qcom_scm_pas_auth_and_reset(GPU_PAS_ID 13)` — those
   **signed MDT segments are vendor-only and NOT in linux-firmware** (WHENCE not
   fetched). So the blocker is refined from "3 proprietary blobs absent" to
   "2 public microcode blobs + a public ZAP .mbn, but the signed MDT/b00/b01
   segment chain and TrustZone PAS authentication are device-vendor-only".
3. **The compiler is NOT a blocker.** Mesa Turnip is a Vulkan 1.3 driver for
   Adreno 6xx GPUs with a shared IR3/NIR compiler; `freedreno_devices.py` has
   `GPUId(630)`, `CHIP.A6XX`, `[a6xx_base, a6xx_gen1, GPUProps(QCTDD04536579 =
   True)]`, `num_ccu = 2`, `highest_bank_bit = 15`, `macrotile_mode = 0`.
   ⇒ the user-space path metal2vulkan → SPIR-V → Turnip NIR → IR3 described in
   the Coolapk article is NOT blocked by the generation. Only the XNU kernel
   backend differs.
4. **The wire ABI is generation-independent** (see architecture section): an A630
   GEN1 backend can implement the same `NativeAdrenoTransport`, but the existing
   backend's GMU cold-start / `ShengGmu.h` platform layer is GEN2/"sheng"-specific
   (`ShengGmu.h` is NOT in this checkout) and must be replaced.
5. **A630 is legacy GMU HFI v1 / SPTPRAC.** `kits/AdrenoFirmware/AdrenoHfi.h:23`
   verbatim 「Modern (nonlegacy) GMU HFI only.」 ⇒ that kit explicitly EXCLUDES
   the A630 path; an A630 backend needs its own HFI v1 (`a6xx_hfi.c`:
   `supported_version = (1 << 28) | (1 << 19) | (1 << 17);` for "version 1.10",
   response queue id `gmu->legacy ? 4 : 1`, 2 queues × SZ_4K, 16 KiB hfi),
   flat-ITCM GMU firmware load (`gmu_write_bulk(REG_A6XX_GMU_CM3_ITCM_START, ...)`,
   no block header), SPTPRAC enable (`GX_SPTPRAC_POWER_CONTROL 0x778000`), and
   RPMh/PDC (`pdc_address_offset = 0x30080`, `RSCC_PDC_SEQ_START_ADDR 0x4520`).
6. **GPU SMMU SID/mask is UNVERIFIED.** Neither mainline v6.12 `sdm845.dtsi`
   (3857 lines) nor downstream msm-4.9 `sdm845.dtsi` (127709 B) has a GPU node;
   GPU + `kgsl-smmu` nodes are in the board DTS. `Mu-Silicium/Resources/DTBs/
   enchilada.dts` could NOT be fetched (jsdelivr @main/@master → 404
   `Couldn't find the requested file /DTBs/enchilada.dts in Mu-Silicium/Resources.`;
   `api.github.com/repos/Mu-Silicium/Resources` → 404). ⇒ the previously cited
   vendor-DTB values (`arm,smmu-kgsl@5040000`, `qcom,kgsl-3d0@5000000
   reg=<0x5000000 0x40000 0x5061000 0x800 0x509e000 0x1000>`, IRQ 300,
   `qcom,chipid=<0x6030001>`) are **not re-verified from a fetched source in this
   round**; do NOT assert a GPU context bank or stream id. Downstream mechanism
   only: `KGSL_IOMMU_CB0_OFFSET 0x8000`, `KGSL_IOMMU_CB_SHIFT 12`, 2 banks
   (`KGSL_IOMMU_CONTEXT_USER = 0`, `..._SECURE = 1`), SMMUv2 ctx regs
   `SCTLR 0x0 / TTBR0 0x20 / FSR 0x58`, VA `KGSL_IOMMU_VA_BASE64
   0x500000000ULL`, `struct a6xx_cp_smmu_info` magic `0x241350D5`.
7. Official subpages `https://unixnu.com/zh/drivers/adreno740` and
   `.../adreno-metal` are A740/SM8550-only (run path 「Metal → AdrenoMetal →
   metal2vulkan → Turnip → Darwin KMD → Adreno740 → A740.」). Neither states
   support for other generations (both served truncated — absence is NOT an
   exclusion claim).

## What the evidence does and does NOT establish

**Establishes (host-verified):**
- A SHA-pinned, reproducible derivation of the A630 (A6XX GEN1) hw_init register
  map using UniXNU's own upstream method, with the exact A6XX variant selection
  (first-file-wins) and the A630-specific `a630_hwcg` / `a630_protect` tables.
- A concrete, generation-measured register delta: A6XX GMU CGC `0x09309` vs A7XX
  `0x23b09`; 105 vs 54 hwcg entries; 32 vs 46 protect writes; 4 A7XX-only
  registers correctly excluded.
- Honest correction of four stale feasibility claims (chip-id register, firmware
  availability, compiler support, ABI generation dependence).

**Does NOT establish (honest boundaries — do not overclaim):**
- No chip-id register offset exists to "source"; chipid is a DT equality.
- No GPU SMMU SID/mask or context bank — the board DTS was not fetchable.
- No CI compile, no flash, no device verification, no register read, no firmware
  load, no GMU/HFI start, no command submission, no rendered image.
- The signed ZAP MDT/b00/b01 segment chain and TrustZone PAS auth are
  device-vendor-only; the three public linux-firmware blobs alone are insufficient
  for a ZAP shader.
- The A6XX GEN1 kernel backend is NOT implemented: CP/IRQ/ring (A7XX-specific in
  upstream), legacy GMU HFI v1 / SPTPRAC / RPMh-PDC cold start, and the
  `ShengGmu.h` GEN2 platform layer replacement are all still open.
- No claim that the scheduler/GPU is correct, deadlock-free, or race-free.
- `scripts/data/adreno-a630-inputs.json` pins Linux **v6.12 torvalds** sources,
  NOT the `ianchb/sm8550-mainline` fork pinned by upstream `adreno-inputs.json`;
  this is intentional (A630 is mainline) but means the two derive inputs are not
  byte-comparable across generations.
